## 1. Purpose and release verdict

Flow's durable core is ready for a first tagged release after a small, defined
hardening pass. The specification, six-table model, journal allocation,
set-oriented decisions and claims, attempt fencing, lease recovery, and Plan 7
maintenance behavior have all received extensive PostgreSQL and race coverage.
This review found no new path by which two workers can both durably settle the
same command.

The current tree should **not** be tagged as v0.1.0 yet. One reachable
dependency vulnerability is a release blocker, a panic in a user commit
function terminates the whole process and then crash-loops through lease
recovery, two newly added public read functions can return an unbounded
number of rows, the queries behind those functions and two existing
inspection paths lack matching indexes, and a blocked user observer can
prevent runtime shutdown. The repository also has no CI workflow or license
file, so a published release would have no automated merge gate or clear
reuse terms.

Plan 8 closes those finite gaps and then publishes v0.1.0 from a verified
`master` commit. It is not a second performance project and it does not reopen
the architecture decisions completed by Plans 1 through 7.

## 2. Confirmed findings and why they are worth fixing

### 2.1 Reachable `golang.org/x/text` vulnerability — release blocker

The planned-at build selects `golang.org/x/text v0.31.0`. Official
`govulncheck` reports
[GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970), also published as
CVE-2026-56852: crafted invalid UTF-8 can trigger an infinite loop in the
normalization package. The call graph reaches the affected code from Flow's
runtime through pgx connection configuration. The advisory is fixed beginning
with `x/text v0.39.0`; the latest observed release during planning was v0.40.0.

This is not theoretical dependency tidiness. A reachable infinite-loop path in
runtime connection setup is unacceptable in the first release. The fix is to
upgrade the complete selected module graph, not to add a local workaround or
overstate which external inputs can reach it.

The planning snapshot also found these direct or selected updates:

- `github.com/goware/pgkit/v2` v2.9.0 to v2.9.2;
- `golang.org/x/sync` v0.18.0 to v0.22.0; and
- `golang.org/x/text` v0.31.0 to v0.40.0.

`github.com/google/uuid v1.6.0` and `github.com/jackc/pgx/v5 v5.10.0` were
already current. `go list -m -u all` also showed newer selected transitive
modules. These versions are a planning snapshot, not pins: implementation must
repeat the inventory and use the latest non-retracted versions available at
that time.

### 2.2 Public by-key reads are input-bounded but output-unbounded

`LiveWorkByKeys` and `HistoryByKeys` accept at most 200 keys, but neither limits
the result set:

- one live key can identify an execution with many queued commands; and
- one permanent or repeatedly reused live key can identify an arbitrarily long
  journal history across executions.

Both functions accumulate all rows into Go slices before returning. The
history call can therefore become an increasingly expensive query and a large
allocation as an installation ages. Limiting the number of input keys does not
bound memory, query duration, result decoding, or transaction lifetime.

These functions were intentionally added for domain-side inspection and should
remain available in bounded form. Because there is no release tag yet, v0.1.0
is the right boundary to replace them rather than preserving unsafe wrappers
and carrying avoidable compatibility debt.

### 2.3 Four read shapes lack suitable leading indexes

The current execution key index begins with `definition_name`, while the two
by-key reads filter only by `execution_key`. It cannot efficiently find an
arbitrary batch of keys. Two older inspection paths have similar gaps:

- default `ListExecutions` orders globally by
  `(created_at DESC, execution_id DESC)`, but the existing list index begins
  with `definition_name`; and
- `GetQueueDepth` filters only by `queue`, while the delivery indexes begin
  with handler name/version or execution ID.

These are small, understandable indexes for user-facing reads. They are worth
adding only with exact production-query plan tests and a write-path regression
check, because the queue table is frequently mutated.

The execution counters also lack the obvious defensive relationship
`open_commands <= command_count`. Runtime code maintains that invariant, but a
named database check is cheap protection against corruption or future query
mistakes.

`GetQueueDepth` also evaluates volatile `clock_timestamp()` separately in its
ready, delayed, and oldest-ready aggregate filters. A row whose `next_run_at`
falls between two evaluations can be counted as neither ready nor delayed.
All aggregates in one snapshot should use one statement-stable timestamp.

### 2.4 A blocked observer can block `Runtime.Run` and `Stop`

Observation delivery is correctly isolated behind one bounded, non-blocking
queue. Shutdown, however, closes the queue and waits unconditionally for the
delivery goroutine. That goroutine invokes arbitrary user code with
`context.Background()`. An observer that blocks forever therefore prevents the
runtime from finishing shutdown forever.

Observers are explicitly best-effort diagnostics and cannot be allowed to own
the durable runtime lifecycle. The smallest fix is to give delivery an
adapter-owned cancellable context, cancel it during close, stop accepting new
observations, and return without an unbounded wait. A callback that ignores its
context may retain at most the one delivery goroutine it blocked; Go cannot
forcibly terminate arbitrary user code. The runtime itself must still return.

### 2.5 The repository has no automated release gate

There is no `.github/workflows` directory, and the open PR has no status checks.
The local verification discipline is strong, but it is not automatically
enforced on every contribution. A compact PostgreSQL 17/18 workflow should
make formatting, module tidiness, build, vet, ordinary tests, race tests, and
vulnerability scanning visible before merge.

This is worth doing now because v0.1.0 creates the first external compatibility
point. It does not require a deployment system, coverage service, release bot,
or elaborate platform matrix.

### 2.6 A release needs explicit legal and compatibility terms

The repository has no `LICENSE`. The recommended default is MIT, matching
`goware/pgkit`, with the repository owner's confirmed copyright wording. This
is a human/legal choice: confirm it before adding the file and do not invent an
owner or contact address.

The README also needs concise supported Go/PostgreSQL versions, retention
expectations, v0.x API compatibility, and forward-only migration policy. These
statements are more valuable for v0.1.0 than additional architecture prose.

### 2.7 A panicking commit function crashes the whole process — release blocker

Handler panics are recovered and classified (`invokeWorker` in
`command_runtime.go`), but a user `WithCommit` function runs later, inside
`SettleCommandSuccess` (`internal/store/commands.go`), with no recover
anywhere on the path. The commit closure executes on the `executeClaim`
goroutine, whose only deferred call is `workerGroup.Done()`, so the panic
unwinds off the goroutine and terminates the entire process, taking every
other in-flight handler with it.

Because the command remains unsettled, lease recovery reschedules it, and
every replica that claims it panics again: one deterministic panic in one
commit function becomes a fleet-wide crash loop that the retry policy never
gets to classify. This is the same defect class as the observer shutdown
finding — arbitrary user code must not own the runtime's fate — and it is
asymmetric with the existing handler-panic contract. Section 4.7 defines the
fix.

### 2.8 `Migrate` is not idempotent for mixed-case schemas

`migrationLedgerExists` (`migrations.go`) probes `SELECT to_regclass($1)`
with the unquoted string `schema + ".flow_schema_migrations"`.
`pgschema.Validate` accepts mixed-case schema names and all DDL quotes them
case-preserved, but `to_regclass` case-folds the unquoted identifier. For a
schema such as `MySchema` the probe returns NULL, a second `Migrate` run
believes the ledger is missing, re-applies 001, and fails on a duplicate
relation — and checksum verification is silently skipped on that path,
because verification only runs when the ledger is reported present. The
default `public` schema is unaffected, which is why tests have not caught
it. Section 4.8 defines the fix.

### 2.9 `ExpireCommandWait` silently swallows real query errors

In `internal/store/graph.go`, the wait-expiry scan checks row values before
the scan error:

```go
if errors.Is(err, pgx.ErrNoRows) || state != "pending" || semantic.DBNow().Before(deadline) {
    return false, nil
}
if err != nil { ... } // unreachable
```

On any non-`ErrNoRows` error, `state` is still empty, the first condition is
true, and the function returns `(false, nil)`; the `MapError` branch is dead
code. Maintenance then reports the pass as a noop instead of an error, so a
persistently failing wait-expiry transition is invisible to operators. No
durable state is corrupted — nothing was written — but a documented
maintenance error path can never fire. Section 4.8 defines the fix.

### 2.10 Keyed starts on caller-owned transactions bypass the lock-order guard

`Event.Deliver`, `CancelCommand`, and `CancelExecution` route through the
transaction-local `LockOrder` guard, which rejects descending execution lock
requests and any Flow operation after the application-write phase begins.
`Command.Execute` does not: `executeStart` uses the raw transaction path, and
a keyed start that rediscovers an existing execution takes `FOR UPDATE` on
that execution's row with no `BeforeExecution` registration
(`loadEquivalentStart` in `internal/store/ingress.go`). Two caller-owned
transactions combining keyed starts and deliveries in opposite orders can
deadlock, resolved only by PostgreSQL's deadlock detector, and the
application-phase guard is bypassed by the same route. The guard exists
precisely to prevent this; Section 4.8 extends it to the start path.

### 2.11 Deadline expiry emits observations for work that was discarded

`SettleCommandSuccess` correctly rechecks the execution deadline under the
execution lock. When it has elapsed, it expires the execution, commits that
terminal transition, and returns `{Status: "expired"}` without persisting the
worker's staged events, children, result, or commit callback. `executeClaim`
ignores the returned status: every nil error emits `event/settle/accepted` for
each discarded event and `attempt/settle/succeeded` for the command.

Durable state is correct, but operational consumers are told that facts were
accepted when they do not exist. Branch on the returned settlement status and
emit one truthful expired/discarded outcome with no accepted-event
observations.

### 2.12 Deterministic early conclusions can use an already-expired context

Argument-decode and duplicate-event-input failures call `concludeClaim` with
the attempt context. With a short attempt deadline, that context can already be
expired before the conclusion transaction begins; all bounded settlement
attempts then fail immediately, the function returns without an observation,
and lease recovery repeats the same deterministic failure indefinitely.

Use a detached conclusion context for these deterministic failures, as
the later result-encode and invalid-decision paths already do. Both settlement
retry loops must emit one bounded error observation if every attempt is
exhausted; they must not silently abandon a still-owned attempt.

### 2.13 Applied migration versions are not required to form a prefix

`verifyAppliedMigrations` validates each ledger row it sees, but does not
require the applied versions to be contiguous from 1. A supported external
`MigrationFS` runner can therefore leave `{1,3}`; a later `Migrate` call sees
version 2 missing and applies it after 3. Migration order is part of the durable
contract even when the current SQL happens not to conflict.

Reject a non-contiguous applied set before applying any migration. Test empty,
valid prefix, missing-middle, and unknown/future ledger shapes.

### 2.14 `Trace` has one avoidable global scan and an isolation caveat

`TraceOperationalInTx` filters `flow_command_event_waits` by `execution_id`,
but the only execution-leading index is partial to unresolved waits. A trace
that includes satisfied waits can therefore scan the global wait table. Rewrite
that read through the execution's commands so PostgreSQL can use the retained
`flow_commands (execution_id, command_id)` ownership index and the waits
primary key; do not add another wait-table index.

Flow-owned `Trace` already creates a Repeatable Read snapshot. A caller-owned
transaction inherits the caller's isolation: under Read Committed, its history,
execution head, and operational projections may come from different statement
snapshots. Do not add a long-lived row lock or silently change a caller's
isolation in this release. Correct the functional spec and API documentation:
callers requiring a coherent trace must use the Runtime client or supply a
Repeatable Read/Serializable transaction.

### 2.15 `flowtest.RunDirect` does not validate a negative command ceiling

`RunDirect` treats zero as its default but does not reject a negative
`maxCommands`. A root-only tree can succeed with the invalid value, while a
tree with a child later reports the misleading “command ceiling exceeded.”
Reject negative input at entry so the test engine mirrors runtime option
validation.

### Invariants that must remain true

1. Flow retains exactly six tables.
2. Every execution mutation still locks the execution before its child
   projections.
3. Only the current attempt ID and lease token may durably settle a command.
4. Handler bodies remain at-least-once; takeover can overlap a stale handler,
   while its settlement is rejected.
5. The journal remains append-only and positions remain contiguous per
   execution.
6. Notifications remain hints for immediately runnable work; correctness still
   comes from polling.
7. All SQL remains schema-qualified and transaction-scoped clients continue to
   observe their own uncommitted writes.
8. Migrations 001 and 002 are immutable after this plan begins. Schema changes
   are forward-only through migration 003.
9. PostgreSQL durability settings are not relaxed in production or in release
   evidence.

## 4. Detailed design

### 4.1 Upgrade the complete selected dependency graph

Define “latest” precisely: the latest non-retracted version for every module
path selected by Flow's packages and tests at implementation time. Do not add
unused modules merely because they have newer releases. If a direct dependency
has a new semantic-import major, evaluate and adopt it when its API remains in
scope; do not rewrite unrelated code just to select an unused incompatible
module path.

Use this sequence and preserve its output in the PR description or a small
release evidence section:

```text
go version
go list -m -u all
go get -u all
go mod tidy
go list -m -u all
go mod verify
go mod tidy -diff
go test -count=1 -p 1 -parallel 4 ./...
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

The second inventory must show no applicable update remaining in the selected
graph. Explain any module that still reports a newer version because of a
retracted version, incompatible module path, upstream constraint, or Go version
requirement. Do not silently retain a known-vulnerable version.

Keep the `go` directive as Flow's minimum supported toolchain contract unless a
dependency genuinely requires a newer minor version. Use the latest patch of
the supported Go minor in CI. Do not mechanically change `go 1.26.4` to the
developer workstation's patch version merely because Go 1.26.5 performed the
upgrade.

After upgrades, inspect pgx/pgkit release notes and compile errors for connection
configuration, transaction, error-mapping, notification, and migration changes.
No application behavior should be changed to “make the tests pass” without
identifying the upstream semantic difference.

### 4.2 Replace unbounded reads with paged APIs

Remove the two unbounded pre-release functions and replace them with these
conceptual public shapes. Exact field comments and names should follow existing
Flow style:

```go
const (
    DefaultReadPageSize = 100
    MaxReadPageSize     = 1000
)

type LiveWorkFilter struct {
    Keys     []string
    PageSize int
    Cursor   string
}

type LiveWorkPage struct {
    Work       []LiveWork
    NextCursor string
}

func ListLiveWork(ctx context.Context, c Client, filter LiveWorkFilter) (LiveWorkPage, error)

type KeyedHistoryFilter struct {
    Keys     []string
    PageSize int
    Cursor   string
}

type KeyedHistoryPage struct {
    Entries    []KeyedHistoryEntry
    NextCursor string
}

func ListHistoryByKeys(ctx context.Context, c Client, filter KeyedHistoryFilter) (KeyedHistoryPage, error)
```

Keep `MaxReadKeys = 200`. Normalize both filters before SQL:

- zero page size means 100; valid explicit sizes are 1 through 1000;
- zero keys returns an empty page and no cursor;
- each key must be non-empty, valid UTF-8, and at most 1024 bytes;
- deduplicate and bytewise-sort a private copy of keys so caller slices are not
  mutated and normalization matches the SQL `C` collation; and
- reject malformed, wrong-kind, wrong-version, or wrong-filter cursors with
  `ErrInvalid`.

Use opaque URL-safe base64 cursors containing only a version, query kind,
normalized-key fingerprint, and the last stable ordering tuple. They need not
be signed: they are untrusted validated input, not authorization. A cursor is
valid only with the same normalized key filter and API kind. Compute the
fingerprint as SHA-256 over a version byte followed by each normalized key as a
four-byte big-endian length and its UTF-8 bytes; do not hash ambiguous string
concatenation. Reject an encoded cursor larger than 4096 bytes before decoding,
strictly decode exactly one object with no unknown fields or trailing data, then
validate every decoded enum, timestamp, UUID, and string bound before SQL.

Use stable immutable orders:

```text
live work:
  execution_key COLLATE "C" ASC,
  definition_name ASC,
  execution_created_at ASC,
  execution_id ASC,
  command_id ASC

keyed history:
  execution_key COLLATE "C" ASC,
  definition_name ASC,
  execution_created_at ASC,
  execution_id ASC,
  journal_position ASC
```

The explicit `C` collation makes Go's UTF-8 bytewise key normalization and the
database order agree regardless of the database's locale. `next_run_at` is
mutable and must not be part of a pagination cursor. Global `recorded_at` order
across executions is not stable enough for a grouped key cursor and is not a
durable total order. Document the new history order as deterministic
key/definition/execution chronology, with journal order preserved inside each
execution.

Each store query must:

- use tuple keyset predicates matching the relevant order;
- request `pageSize + 1` rows and never more;
- retain transaction-aware `pgx.Tx` reads;
- derive `NextCursor` from the last returned row only when the look-ahead row
  exists;
- discard the look-ahead row before public decoding; and
- preserve all existing enum, body-hash, and durable-state validation.

Both store row types need `execution_created_at` for ordering and cursor
construction. Treat it as internal pagination state; do not add it to
`LiveWork` or `KeyedHistoryEntry` merely because the SQL must scan it.

Do not retain deprecated wrappers that concatenate every page. That would
preserve the defect under a different implementation.

Pagination guarantees a bounded response, not a cross-page snapshot on an
ordinary client. Live queue rows can move or disappear between calls. The
immutable tuple order prevents updates to scheduling fields from reshuffling
remaining rows; callers needing a transaction snapshot may use the existing
transaction-scoped client. Journal rows are append-only, so already traversed
history remains stable.

### 4.3 Add forward migration 003 for release read paths

Do not edit `001_initial.sql` or `002_live_keys.sql`. Add
`migrations/003_release_read_paths.sql`, register it as schema version 3, and
exercise both clean installation and an actual version-2 upgrade. This makes
the existing migration checksums the durable pre-v0.1 baseline.

Register migration 003 as `release_read_paths` with minimum reader and writer
versions still at 1. It adds enforcement and access paths but no durable field
that an older reader/writer must understand. Preserve the existing behavior by
which a runtime verifies the exact current schema version before starting.

Migration 003 should make only these changes:

1. Add a key-first index for exact by-key lookup and keyset pagination, and
   retain `flow_executions_key_prefix_idx` unchanged:

   ```sql
   CREATE INDEX flow_executions_key_lookup_idx
       ON {{schema}}.flow_executions
          (execution_key COLLATE "C", definition_name,
           created_at, execution_id);
   ```

   **Why this index is additive.** A prior design considered
   `text_pattern_ops` and replacing the definition-first prefix index. Retain
   both final choices here because:

   - `text_pattern_ops` uses pattern-comparison operators rather than the
     ordinary comparison family. It cannot serve the ordinary `ORDER BY`
     pathkeys or tuple keyset comparisons Section 4.2 requires. A
     `"C"`-collated btree with the default operator class serves ordinary
     comparison, tuple keysets, equality, and LIKE-prefix bound derivation;
     and
   - dropping the definition-first index would structurally regress
     `ListExecutions` with a definition name and key prefix: a key-first
     replacement scans the prefix range across all definitions and
     post-filters, which a fixture plan test cannot distinguish from the
     selective path. The old index therefore stays, and the existing
     `ListExecutions` SQL is not rewritten and keeps its current collation.

   Both paged queries must write `execution_key COLLATE "C"` explicitly in
   every predicate and `ORDER BY` so the planner matches the new index's
   collation; no other query adopts the explicit collation. Keep the new
   index non-partial: a `WHERE execution_key <> ''` variant was considered
   and rejected because parameterized key predicates cannot reliably prove
   the partial predicate under generic plans. Unkeyed executions therefore
   index under the empty key; the paged APIs never search for it because key
   validation rejects empty keys.

   Plan tests must demonstrate the intended paths on PostgreSQL 17 as well as
   18: PostgreSQL 18's btree skip scan can partially mask a missing leading
   column and must not be allowed to green a test that 17 would fail.

2. Add the missing default execution-list order:

   ```sql
   CREATE INDEX flow_executions_created_idx
       ON {{schema}}.flow_executions
          (created_at DESC, execution_id DESC);
   ```

3. Add a queue-leading operational depth index:

   ```sql
   CREATE INDEX flow_command_queue_depth_idx
       ON {{schema}}.flow_command_queue
          (queue, state, next_run_at);
   ```

4. Add the named defensive counter relationship:

   ```sql
   ALTER TABLE {{schema}}.flow_executions
       ADD CONSTRAINT flow_executions_open_commands_ck
       CHECK (open_commands <= command_count);
   ```

The migration runner uses one transaction per file, so do not introduce
`CREATE INDEX CONCURRENTLY`. At this pre-v0.1 boundary, ordinary transactional
DDL is preferable to changing the migration protocol. Document that operators
should run schema migrations before starting the new binary, as already
required by the exact schema-version check.

Add exact catalog assertions for names, columns, order/opclass, predicates,
uniqueness, and the counter check. Preserve the six-table inventory. Test an
upgrade fixture that applies the unchanged 001 and 002 files, records their
checksums, upgrades through 003, and verifies those checksum rows did not
change.

For query-plan tests, use the exact production SQL builders against selective
fixtures large enough to discourage a sequential scan. Assert an appropriate
index path for:

- live work by exact key batch;
- history by exact key batch;
- unfiltered `ListExecutions` order and cursor;
- `GetQueueDepth` for a selective named lane; and
- `ListExecutions` with both definition name and literal key prefix.

Do not force planner cost settings as the only proof. It is acceptable for a
tiny table to choose a sequential scan; retain a non-cost-forced selective
fixture that demonstrates the intended path.

The queue-depth index adds write work to every queue mutation, and retaining
the prefix index means the key-lookup index is a net addition to
`flow_executions` writes. Establish the baseline after Phase 1 dependency
upgrades but before Phase 2 source/migration changes, then compare that exact
commit with the Phase 2 candidate on fresh schemas on the same PostgreSQL
server. Run five interleaved or immediately adjacent samples of the existing
execution ingress, independent lifecycle, and same-execution fan-out
benchmarks; ingress exercises the `flow_executions` write path, so both

### 4.4 Make observer shutdown best-effort in both directions

Preserve one adapter, one bounded queue, non-blocking emit, panic isolation,
and aggregate dropped-observation accounting. Do not create a goroutine per
observation.

Give the adapter one `context.WithCancel(context.Background())` context. Pass
that context to every `Observer.Observe` call. During `close`:

1. atomically stop accepting new observations;
2. cancel the observer context;
3. close or otherwise stop the queue exactly once; and
4. return without an unbounded wait for arbitrary observer code.

Well-behaved observers should return promptly when the context is cancelled.
An observer that ignores cancellation may strand the one delivery goroutine it
currently occupies, but it must not strand `Runtime.Run`, `Runtime.Stop`, the
scheduler, workers, leases, maintenance, or database resources. Queued
observations may be abandoned during shutdown; this is consistent with the
best-effort contract.

Add deterministic tests that:

- block an observer callback, stop the runtime, and prove shutdown returns
  before the test releases the callback;
- prove the callback context is cancelled;
- unblock the callback during test cleanup and prove the delivery goroutine can
  finish;
- preserve ordinary delivery, bounded drop reporting, panic isolation, and
  emit-versus-close race safety; and
- pass repeatedly under the race detector.

Update `Observer` documentation, README, `doc.go`, and the runtime component
only enough to say that delivery and shutdown drain are best-effort, observers
must return promptly and should honor context cancellation, and observation
loss never changes durable correctness.

### 4.7 Isolate user commit-function panics

Recover the panic inside the runtime-owned commit closure in
`command_runtime.go` — not inside `internal/store`, which must keep returning
`CommitFunctionError` unchanged. A recovered panic converts to an error
return from the closure, so the settlement transaction rolls back through the
existing `CommitFunctionError` path, and the claim concludes with the panic
classification exactly as a panicking handler does: the attempt is consumed
and the retry policy may drive the command permanent.

Use one private sentinel or typed error such as `errCommitPanicked`. The closure
must use a named error result and a defer that replaces any recovered value with
that sanitized marker; never format the recovered value. In the existing
`CommitFunctionError` branch, recognize the marker and call the same
`ClassPanic` conclusion path used for handler panics. An ordinary returned
commit error retains its current classification.

Requirements:

- the `executeClaim` goroutine must be unable to terminate the process
  through any user commit function, including one that panics after issuing
  writes on the settlement transaction — those writes roll back with the
  transaction;
- the conclusion must record a bounded, sanitized failure message consistent
  with existing panic handling; never journal raw panic values beyond the
  current failure-message limits;
- sibling in-flight commands, the scheduler, leases, and maintenance must be
  unaffected; and
- `flowtest.RunCommit` is intentionally untouched: it is a test helper, and a
  panic there should surface to the test that caused it.

Add deterministic tests proving a panicking commit function settles the
command as a classified failed attempt on a live runtime, that the settlement
transaction's partial writes are rolled back (the existing
`SettleBeforeCommitFunction`/`SettleAfterCommitFunction` fault hooks bracket
the call), that unrelated commands complete normally, and that the behavior
holds repeatedly under the race detector.

### 4.8 Targeted release correctness fixes

These small, contained fixes ride along with the release because each closes a
confirmed defect in an area this plan already touches. None changes a public
signature.

1. **Migration-ledger probe (Section 2.8).** Probe ledger existence with the
   fully quoted, case-preserved qualified name —
   `quoteIdentifier(schema) + "." + quoteIdentifier("flow_schema_migrations")`
   — or query the catalog the way `verifyFlowTables` already does. Add a
   mixed-case schema fixture that runs `Migrate` twice and proves the second
   run is a verified no-op whose checksum verification actually executed.

2. **Wait-expiry error ordering (Section 2.9).** In `ExpireCommandWait`,
   check the scan error before interpreting row values so real errors reach
   `MapError` and the maintenance pass reports an error outcome. Prove it
   with a database-backed regression that forces this query/scan to fail in an
   isolated schema: a failing wait-expiry query must produce an error
   maintenance observation, not a noop. Do not add a production fault point
   solely to test this branch.

3. **Keyed-start lock ordering (Section 2.10).** Extend the internal start path
   to receive the transaction client's `LockOrder` (nil for an ordinary pooled
   client). Add an application-phase-only check and run it before the first
   start SQL. Register `request.ID` before the created-row path. On idempotent
   conflict, resolve the actual execution ID without a row lock, call
   `BeforeExecution(actualID)`, then take `FOR UPDATE` by that ID and revalidate
   key scope, identity, and live status. If a live holder changes during the
   race window, repeat the existing bounded resolution while registering every
   actual row before locking it; a descending ID must return `ErrInvalidState`,
   not fall through to PostgreSQL's deadlock detector. Do not pre-register only
   `request.ID` for keyed starts and assume it is the existing owner's ID.

   Preserve idempotent start semantics and leave ordinary pooled clients
   unchanged. Test created and rediscovered keyed starts, application-phase
   rejection before SQL, and a descending Execute-after-Deliver sequence in one
   caller-owned transaction.

4. **Queue-depth timestamp (Section 2.3).** `GetQueueDepth` evaluates volatile
   `clock_timestamp()` independently in each aggregate filter, so a row
   crossing `next_run_at` between evaluations counts as neither ready nor
   delayed. Capture one statement-stable timestamp and use it in all three
   expressions.

5. **Deadline settlement observations (Section 2.11).** Capture the
   `SettleResult` instead of discarding it. Emit accepted-event and succeeded
   observations only for `Status == "succeeded"`; for `Status == "expired"`,
   emit one bounded expired/discarded settlement outcome and no event-accepted
   observations. Reject an unknown nil-error status as an internal invalid
   state rather than guessing.

6. **Early and exhausted conclusions (Section 2.12).** Give deterministic
   argument/event-input corruption conclusions the same detached settlement
   context used after handler return. Keep the attempt fence as the
   durable authority. At the end of both the success-settlement and conclusion
   retry loops, emit one bounded `settle/error` or `conclude/error` observation;
   include no raw database error, token, payload, or panic value.

7. **Migration prefix (Section 2.13).** Extend applied-ledger validation to
   require exactly versions `1..N` before any pending unit runs. Preserve the
   existing unknown-version, checksum, name, and compatibility checks. Add a
   direct validation test and a database-backed external-runner hole fixture.

8. **Trace waits and isolation (Section 2.14).** Rewrite the all-waits query as
   an execution-filtered command-to-wait join using the existing command
   ownership index and wait primary key. Add a selective plan test with many
   unrelated satisfied waits. Update Trace documentation to distinguish its
   owned Repeatable Read snapshot from caller-owned isolation; do not add an
   index or acquire a long-lived execution lock.

9. **Test-engine ceiling (Section 2.15).** Reject negative `maxCommands` at the
   beginning of `flowtest.RunDirect`, before invoking application code. Test
   both a root-only and child-producing definition.

- commit-function panic isolation cannot be achieved without adding recover

## 9. Deferred follow-ups (not v0.1.0 release blockers)

The amendment review also identified the following design opportunities. They
are deliberately outside Plan 8 because they require a new policy choice or
write-cost evidence, not because an executor should silently address them while
hardening the release.

1. Staged application events per worker decision have no explicit count cap:
   `Emit` caps each payload but not the count of distinct staged events, so one
   trusted handler can build a very large decision and settlement transaction
   (`worker.go`; contrast `maxCommandEventWaits` and the execution child
   ceiling). Application handlers can already allocate without a library
   bound, so this is not a security boundary. A future plan may add a documented
   per-decision limit after choosing a useful value and compatibility policy.
2. Partial-index and LIKE-prefix matching in `loadEquivalentStart` and
   `ListExecutions` depends on custom plans; `plan_cache_mode=auto` produces
   them for current point queries. Plan 8's tests must use real parameter values.
   Any future partial-index proposal must explicitly account for generic-plan
   predicate proof.
3. These remain deliberate write-cost/ownership tradeoffs and should change
   only with evidence: no uniqueness on `flow_journal.entry_id`, empty strings
   accepted at the database layer for application-validated identity columns,
   and no foreign keys from wait/terminal/created positions to journal
   positions.
